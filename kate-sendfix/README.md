# Kate Mobile 133.7 lite — отправка сообщений при «Flood control»

Патч для `Kate_Mobile_133.7_lite.apk` (package `com.perm.kate_new_6`, versionCode 623,
sha256 `1abe2b86…bd49b4`). Он позволяет отправлять `messages.send` с токеном
**собственного** приложения VK пользователя. Остальные функции Kate работают как раньше.

## А. Диагноз

**Причина (наиболее вероятная, подтверждена косвенно).** С 7 сентября 2026 VK считает
вызовы API отдельно для каждого приложения: 10 000 вызовов в месяц без верификации
бизнес-профиля, 100 000 000 после неё. Kate авторизуется как приложение
`client_id=2685278`, поэтому все её запросы списываются с одной общей квоты. Квота
исчерпана, и сервер отвечает ошибкой `error_code 9, "Flood control"`. Частота отправки
у конкретного пользователя на это не влияет.

**Доказательства по коду APK** (декомпиляция jadx и apktool):

| Звено | Где | Что установлено |
|---|---|---|
| UI → очередь | `com.perm.kate.m` (MessageSendQueue) `.c()` → `n30.k()` → `p0` (case 19) | очередь отправляет по одному сообщению |
| Запрос | `xr0.b()` | `messages.send`: `peer_id`, `message`, `attachment`, `forward(_messages)`, `random_id=System.nanoTime()`, `v=5.212`, captcha-параметры |
| Сеть | `e3.o()` → `e3.p()` | POST на `https://api.vk.ru/method/messages.send`. Повтор максимум 3 раза и **только** при `SocketException`, `SocketTimeoutException` или `SSLException`, с тем же телом и тем же `random_id`, поэтому сервер отбрасывает дубль |
| Ошибка | `e3.o()` | `error_code` и `error_msg` берутся из JSON ответа как есть и упаковываются в `KException` |
| Диспетчер | `qt0.c()` | код 9 входит в список «не отправлять в крэш-лог», повтора нет, ошибка передаётся в UI |
| Очередь при ошибке | `com.perm.kate.k.h()` | сообщение помечается ERROR, автоматических повторов нет |

В APK нет ни одной строки «flood» и нет локального ограничителя частоты. Значит, текст
«Flood control» — это `error_msg` из ответа сервера. Клиент сам его не генерирует и не
путает с другой ошибкой.

**Проверенные гипотезы:**

| Гипотеза | Статус | Как различить на устройстве |
|---|---|---|
| H1. Исчерпана квота приложения Kate (2685278) | подтверждается: сроки (8.09), публичные заявления разработчика, ответ поддержки VK, код | с токеном *другого* приложения тот же аккаунт отправляет то же сообщение без ошибки |
| H2. Реальный флуд-контроль аккаунта | маловероятна | в веб-версии vk.com отправка тоже не проходит |
| H3. Локальный лимитер в Kate | опровергнута | такого кода и строк нет |
| H4. Клиент неверно классифицирует ответ | опровергнута | код 9 берётся из JSON без изменений |
| H5. Изменился формат запроса или версия API | не подтверждается | при ошибке формата приходит код 100 или 15, а не 9. `random_id=nanoTime()` выходит за int32 из документации, но так было и раньше, а ошибка 9 с этим не связана. Параметр не трогал |
| H6. Повторные отправки клиентом | опровергнута | ретраи только при сетевых ошибках и с тем же `random_id`, очередь не повторяет |

Почему «чтение работает»: ключ и `ts` LongPoll Kate хранит в настройках (`lpkey_*`,
`ts_*`), а историю — в локальной БД. Поэтому новые сообщения могут приходить и
показываться без вызовов методов API. Это гипотеза, на живом аккаунте я её не проверял.
Если открыть диалог, которого нет в кэше, или обновить список диалогов, при полном
отключении должна появиться та же ошибка.

**VK X.** Это закрытое приложение (разработчик iTaysonLab, vkx.app). Его удалили из
Google Play по жалобе VK, последнее обновление вышло 14.09.2026. Исходников нет, как
оно авторизуется, достоверно неизвестно, поэтому для сравнения на уровне кода оно не
подходит. Публично известно о похожих модах (например, VK mp3 mod): они получают
токен «так же, как официальный клиент». Их вызовы засчитываются приложению самого VK и
под квоту сторонних приложений не попадают. Это объясняет, почему «один клиент
работает, а другой нет»: квоту VK считает по `client_id`, на который выписан токен.

**Почему патч не подменяет Kate официальным клиентом VK.** Это решило бы проблему
у всех, но означает использовать чужие учётные данные (client_id и secret
официального приложения VK), чтобы обойти ограничение, которое VK ввёл намеренно.
Это нарушает правила VK и ставит под угрозу аккаунт пользователя. В патче этого нет.

## Б. Изменения

Патч: `patches/kate-133.7-lite-sendfix.diff`.

| Файл | Изменение |
|---|---|
| `smali/KateSendFix.smali` (новый, исходник — `src/KateSendFix.java`) | логика токена отправки |
| `smali/xr0.smali`, `b()` | `e3Var.o(req, true)` заменён на `KateSendFix.send(e3Var, req, qt0.b.a)` |
| `smali/com/perm/kate/LoginActivity.smali`, `onCreate()` | если открыто с extra `send_token`, загружается `oauth.vk.ru/authorize?client_id=<свой API ID>&scope=messages,offline&response_type=token` |
| `smali/com/perm/kate/LoginActivity.smali`, `H()` | в режиме `send_token` редирект `blank.html#access_token…` обрабатывается отдельно, а основная сессия Kate не меняется |
| `res/xml/preferences.xml` | «Настройки → Сообщения → Отправка через своё приложение VK»: описание, поле «API ID», пункт «Получить токен отправки» |
| `apktool.yml` | versionName `133.7 lite-sendfix` |

Поведение `KateSendFix.send`:

* Токена отправки нет, то есть по умолчанию: запрос идёт основным токеном, как раньше.
  Если сервер вернул код 9, сообщение выглядит так: `Flood control` плюс подсказка, что
  речь о квоте `client_id 2685278` и где задать свой API ID. Код ошибки остаётся 9.
* Токен есть: `messages.send` идёт им, один запрос, тот же `random_id`.
* Код 9 на своём токене пробрасывается **без** fallback и с пометкой «лимит вашего
  приложения или реальный флуд-контроль». Настоящая серверная защита от флуда
  сохраняется.
* Коды 4, 5, 17, 25 на своём токене означают проблему именно токена отправки.
  Токен удаляется, и запрос повторяется основным токеном. Так `qt0` не запускает для
  основной сессии повторный вход, валидацию или `auth.refreshToken`.
* Капча (14) пробрасывается с `captcha_sid` и `captcha_img`. Kate показывает капчу и
  повторяет запрос тем же токеном.
* Коды 7 и 15 дополняются подсказкой «приложению не выдан доступ к messages».
  Все остальные ошибки передаются без изменений.
* Токен хранится в отдельном файле `kate_send_tokens` под ключом `token_<user_id>`.
  Он не попадает в экспорт настроек Kate. Токен другого аккаунта не используется.
  Никуда, кроме `api.vk.ru`, токен не передаётся.

## В. Сборка

```
./build.sh /path/Kate_Mobile_133.7_lite.apk [work_dir]
```

Скрипт запускает логические тесты, затем apktool d, `patch -p1`, apktool b и подпись
(uber-apk-signer, v1/v2/v3). Результат проверен: сборка из оригинального APK проходит,
подпись верифицирована, `classes.dex` при повторной сборке совпадает побайтно, весь dex
без ошибок разбирается D8.

Подпись отличается от оригинальной, поэтому поверх Kate APK не встанет. Нужно
экспортировать настройки в Kate, удалить её и установить собранный APK. Для будущих
обновлений сохраните `work/sendfix.jks` и никому его не передавайте.

## Г. Проверка

Проверено автоматически:

* `test/SendFixTest.java`: 31 проверка логики (успех, код 9 на обоих токенах, fallback
  при 4/5/17/25, капча, 15, прочие ошибки, разбор OAuth-редиректа, привязка к user_id,
  ошибка авторизации). Тест запускается на JVM с подменными Android-классами.
* Пропатченные методы декомпилируются jadx в ожидаемый код.

Не проверено (нет учётной записи VK и Android-устройства):

* реальный ответ VK на токен своего приложения;
* выдаёт ли VK новым приложениям право `messages` через Implicit Flow. По отзывам, новые
  приложения могут получать «This application has no right to use messages»;
* как работает `offline`-токен и учитывается ли он в квоте 10 000 вызовов в месяц;
* отображение настроек и работа LoginActivity в ART.

Как проверить на устройстве:

1. Создайте Standalone-приложение VK (vk.com/apps?act=manage или кабинет VK ID для
   бизнеса) и включите для него Implicit Flow и redirect `https://oauth.vk.ru/blank.html`.
2. В Kate откройте «Настройки → Сообщения → Отправка через своё приложение VK», введите
   API ID и нажмите «Получить токен отправки». Войдите в **тот же** аккаунт. Должно
   появиться сообщение «Токен отправки сохранён для id…».
3. Отправьте сообщение себе («Избранное») или в тестовый диалог. Убедитесь, что оно
   появилось в веб-версии vk.com и в официальном приложении. Исчезновение ошибки
   доказательством отправки не считается.
4. `adb logcat -s Kate.Api Kate.SendFix`: строка `url=https://api.vk.ru/method/messages.send`,
   и после неё нет исключения.
5. До и после: без токена отправка заканчивается ошибкой «Flood control (токен Kate…)».
   С токеном сообщение доставляется. Если на своём токене приходит «Flood control (токен
   вашего приложения…)», это реальный лимит.

## Д. Если не заработает

* OAuth возвращает `error=…` или «no right to use messages» (код 15): у вашего
  приложения нет доступа к сообщениям. Его нужно запросить у VK
  (devsupport@corp.vk.com). В коде здесь ничего исправить нельзя.
* Implicit Flow на `oauth.vk.ru` для новых приложений VK ID отключён: тогда следующий
  шаг — заменить `startAuth`/`onUrl` на авторизацию VK ID OAuth 2.1
  (`id.vk.ru/authorize`, PKCE, обмен `code` на токен). Остальная часть патча останется
  без изменений.
