# Имитация телефона (phone-imitaion)

Два инструмента, оба уже в репозитории; этот скилл — как их запускать, читать результат и расширять.
Отвечать пользователю по-русски.
- **Стенд сети** (`scripts/test-tun.sh`, `scripts/tunlab/`) — путь трафика, ТСПУ, скорость; ниже до раздела
  «Эмуляторы».
- **Эмуляторы Android** (`scripts/ui-test.py`, job «ui» в `.github/workflows/build.yml`) — настоящий APK
  глазами человека: экраны, меню, подключение, ключ; раздел «Эмуляторы: полная проверка приложения».

Что чем ловится: сеть и обход DPI — стенд; интерфейс, переходы между экранами, Android-сервис целиком,
ключ и его срок, падения процессов — эмулятор. Перед вердиктом владельцу «без багов» — оба зелёные.

Главный принцип: **код приложения настоящий, подделано только окружение.** ByeDPI, tun2socks, перебор
стратегий, проверки и маршруты — те же, что в APK; имитируются телефон (netns + uid), оператор (модель
ТСПУ) и интернет (сайты с адресами из журнала). Поэтому стенд находит ошибки самого приложения
(DNS, задержки, переполнение пула, раннее закрытие сессий), а не только «логику на бумаге».

## Что моделируется

Три сетевых пространства (netns), всё на одной машине Linux:
- **phone** — «телефон»: `tun0` от hev-socks5-tunnel, весь трафик по умолчанию — в tun0.
  ByeDPI и проверки ODA работают от uid 2000 и идут мимо VPN (как `addDisallowedApplication`:
  `ip rule uidrange` + своя таблица маршрутов). «Psiphon» стенда (SOCKS5, `lab.py socks`) — от uid 2001,
  ходит в «интернет» мимо оператора по отдельному каналу p1/s1 (как зашифрованный туннель за границу),
  с задержкой соединения 150 мс и общей полосой 8 Мбит/с (`PSIPHON_DELAY_MS`, `PSIPHON_KBIT`),
  принимает только CONNECT (UDP ASSOCIATE отвергает, как настоящий Psiphon).
- **isp** — «оператор» с **моделью ТСПУ** `scripts/tunlab/tspu.py`: ядро отдаёт весь пересылаемый трафик
  в TUN `dpi0`, программа решает и пишет пакет в `dpi1`. Собирает поток клиента по номерам
  последовательности (поздняя часть перекрывает раннюю), ищет SNI/Host и рвёт соединение (этот и все
  следующие пакеты); `urg` — вырезать байт OOB или оставить; `tls` — искать имя только в первой
  TLS-записи (tlsrec пробивает) или склеивать записи; `ip_block` — сети, где не проходят пакеты с данными;
  `dns_block` — резолверы, к которым не проходит UDP-DNS; фейк с TTL ≤ 6 до сервера не доходит.
  Журнал решений — `tspu.log` («блок …», «пропуск …»).
- **srv** — «интернет»: DNS 1.1.1.1, 8.8.8.8, 9.9.9.9, 77.88.8.8 (как `NetProbe.DNS_SERVERS`), HTTPS-сайты
  с адресами из журналов (`SITES` в `lab.py`: instagram и i.instagram, facebook и graph.facebook, CDN
  картинок, YouTube, googlevideo, x, rutracker, google, cloudflare, wikipedia, ya, vk, gosuslugi),
  «сервер Telegram» 149.154.167.51:443 без TLS (эхо), UDP-эхо 443 на каждом адресе («QUIC»),
  `/big` на любом сайте — 32 МБ для замера скорости.

Профили ТСПУ (`PROFILES` в tspu.py) подобраны по журналам телефона:
- `nov2026` — журнал 0.8.8: как oct2026, instagram по адресу не закрыт, UDP-DNS к 1.1.1.1 и 8.8.8.8
  режется (в 0.8.8 из-за этого все стратегии отвергались и всё шло через медленный Psiphon).
- `oct2026` — журнал 0.8.7: OOB/disoob/fake не пробивают, tlsrec — да; instagram, CDN и Telegram
  закрыты по адресу; YouTube режется по имени для мягкой стратегии.
- `jun2026` — журнал 0.8.6: OOB-семейство пробивает; CDN и Telegram закрыты по адресу.

## Запуск

```bash
git submodule update --init --recursive          # byedpi и hev-socks5-tunnel
python3 -m pip install pyroute2                  # в CI: sudo python3 -m pip install --break-system-packages pyroute2
bash scripts/test-bypass.sh                      # быстро (~1 мин): логика выбора, маршрут, строки ByeDPI
sudo bash scripts/test-tun.sh                    # имитация, ~10 минут; без root сам перезапустится через sudo
LAB_PROFILES=nov2026 sudo -E bash scripts/test-tun.sh   # один профиль (~3–5 минут)
```

Нужны: root, gcc, make, patch, JDK (javac/java), python3 + pyroute2, openssl, curl, procps (pgrep),
util-linux (nsenter, unshare, setpriv). Утилита `ip` не нужна (всё через pyroute2).
Длинный прогон запускать в фоне и ждать завершения (Monitor с grep по «✗|Имитация телефона|EXIT»).
**Не править `test-tun.sh` во время прогона**: bash читает скрипт по ходу и споткнётся о сдвинутые строки.

В CI это шаг «Simulate phone traffic through tun2socks and ByeDPI» в `.github/workflows/build.yml`.
Для веток не `main`/`claude/**` workflow запускается вручную (workflow_dispatch, `build.yml`, ref = ветка);
APK — артефакт `vpn-app-debug`. Локальный зелёный прогон не заменяет CI: на раннере есть IPv6 (как на
телефоне), в контейнере — нет.

## Как читать результат

Для каждого профиля:
1. **Выбор стратегии** — журнал как у приложения («Сеть напрямую …», «DNS напрямую: 1.1.1.1 −, …»,
   «Заблокированные напрямую: … по адресу / по имени», «Обход DPI (стратегия): … · instagram-(TLS)
   facebook+ … · DNS 9.9.9.9», «подключаюсь через …», «DNS телефона: …»). Проверки: выбрана стратегия,
   пробивающая заблокированные; для oct2026 и nov2026 — tlsrec, для jun2026 — OOB; для nov2026 —
   DNS телефона 9.9.9.9 (`chosen.dns`; resolv.conf «телефона» пишется из него).
2. **«Приложения» через VPN** (запасной путь открыт): обычные сайты сразу; YouTube ≤ 12 с; Facebook
   (www и graph) сразу — список доменов; Instagram (www, i.) — в oct2026 ~4,7 с (сильная не прошла →
   Psiphon), повтор сразу; CDN картинок — через Psiphon; Telegram «ok»; QUIC к Meta «fail» (отброшен),
   к Google «ok»; NetProbe и сторож; `dnspair` (A и AAAA с одного сокета, третий запрос сразу и через 3 с —
   все ответы быстрее секунды); сводка ByeDPI с «QUIC (UDP 443): Meta …» и «Telegram → Psiphon».
Только nov2026:
3. **Скорость и задержка** (и «мелкие записи подряд»: ответ быстрее 25 мс через обход и через «Psiphon») — загрузка 32 МБ с cloudflare, facebook, i.instagram, googlevideo: сначала без VPN
   (для сравнения), потом через обход DPI, потом через «Psiphon» (hev с конфигом Psiphon, mapdns).
   Строки «DNS … TCP … TLS … первый байт» показывают, на каком этапе теряется время. Проверки: обход
   ≥ 3× Psiphon и ≥ 2 МБ/с; первый байт через обход < 0,1 с; через «Psiphon» — ≤ его задержка + 0,1 с.
   Плюс кнопка «ТЕСТ СКОРОСТИ» приложения: настоящий `SpeedTest` (`TunLab speedtest`) через SOCKS ByeDPI —
   SOCKS с именем сайта, ByeDPI разрешает его DNS «оператора» (`APPDNS`, resolv 77.88.8.8); сервер загрузки —
   `speed.cloudflare.com` стенда (`/__down?bytes=N`).
   Узкое место стенда — модель ТСПУ на Python (каждый пакет): абсолютные цифры — не цифры телефона,
   важны соотношения и задержки по этапам.
Только oct2026:
3. **Поток DNS** — 15 потоков, 100 запросов/с (`LOAD_RATE`), 40 с, vk.com каждые 5 с: «8 из 8»,
   «pool is full: 0». Без ограничения частоты поток упирается в скорость машины (тысячи запросов/с) — это
   не нагрузка телефона.
4. **Запасной путь закрыт** — обычные сайты, Facebook, YouTube работают; Telegram — нет; «почему»:
   CDN «…по адресу», facebook «…по имени».
5. **Контроль 0.8.6** (без -c, без маршрута, «split SNI → disoob SNI»): соцсети не открываются. Поток DNS
   со старым конфигом с 0.8.9 не роняет интернет (ByeDPI сам закрывает DNS-ассоциации) — «!», не провал.

Итог: «Имитация телефона с обходом DPI: OK» или «ОШИБКА» с хвостами журналов ByeDPI, hev, ТСПУ,
«Psiphon» и HelperRelay.

## Журнал телефона → стенд → исправление

Порядок работы, когда пользователь присылает журнал («ЖУРНАЛ» → «КОПИРОВАТЬ»):
1. Прочитать журнал как данные: какие стратегии «+»/«−» и почему (`-(TCP)` — адрес не соединяется,
   `-(TLS)` — рвут рукопожатие по имени, `-(0 КБ)`/`-(N КБ)` — «замораживают»), «DNS напрямую»,
   «Заблокированные напрямую: … по адресу / по имени», сводки «ByeDPI за 30 с», «Не открывается обходом
   DPI: … — почему», «Запасной путь (Psiphon): …», «Туннель: … пакетов», «Прошлый запуск завершился
   аварийно …» и строки «Журнал Android упавшего процесса».
2. Повторить поведение на стенде: новый профиль в `tspu.py` (или правка), новые адреса в `SITES`, пока
   строки «Обход DPI (…): …» стенда не совпадут с телефонными. Только потом менять приложение.
3. Исправлять в коде приложения (`BypassProfile`, `NetProbe`, `VpnTunnelService`, …), в правке ByeDPI
   (`scripts/byedpi.patch`) или в сборке tun2socks (`app/src/main/jni/oda-hev.h`, `Application.mk`), а не
   в стенде. Проверка, которая должна падать на старом коде, — в `test-tun.sh` через `check <0|1> "текст"`.
4. `scripts/test-bypass.sh` → `test-tun.sh` → push → CI (workflow_dispatch) → зелёный → новый журнал
   пользователя. Если чего-то не хватает в журнале для следующего шага — добавить строку в приложение.

Соответствие строк журнала и стенда:
| Строка журнала телефона | На стенде |
|---|---|
| «DNS напрямую: 1.1.1.1 −» | `dns_block` профиля |
| «instagram-(TCP)», «TCP напрямую не соединяется — по адресу» | `ip_block` |
| «facebook-(TLS)», «на другое имя сервер отвечает — по имени (DPI)» | `sni` + `urg`/`tls` |
| «x-(0 КБ)», «N КБ» | `freeze` |
| «после сбоя: … → disoob SNI после сбоя» (YouTube) | имя в `sni` для мягкой стратегии |
| «Telegram → Psiphon», «split cancel: pos=0--1» | `TG_IP` в `ip_block`, `tgcheck` |
| «QUIC (UDP 443): Meta …» | UDP-эхо 443, `quiccheck` |

## Чего имитация не ловит (и чем это закрыто)

- **Сборка под Android и JNI.** Стенд собирает hev своим `make`, без JNI. В 0.8.9 `cFlags` из Gradle
  затёрли `APP_CFLAGS` из `Application.mk` (переменная командной строки make), JNI_OnLoad искал чужой класс —
  приложение падало при запуске туннеля, а стенд был зелёным. Закрыто проверкой в CI («Check tun2socks in
  APK»: имя класса `com/example/vpnapp/Tun2Socks` и метка `oda-hev.h` в `libhev-socks5-tunnel.so`).
  Флаги нативной сборки — только в `Application.mk`.
- **Логика Android-сервиса** (`VpnTunnelService`: переходы между движками, переход с Psiphon на обход,
  сторож) на стенде не запускается: её стенд повторяет кусками (`TunLab search` — как `startBypass`/
  `decideBypass`). Проверяется эмулятором (job «ui»: подключение, смена способа при подключении, конец
  срока ключа) и журналом с телефона.
- **Настоящий ТСПУ и сеть оператора.** Модель повторяет только известное по журналам; поведение меняется
  (0.8.7 — tlsrec, 27.10 — disoob), поэтому перебор стратегий в приложении важнее любого профиля.
- **Падения на телефоне** видны в журнале: «Прошлый запуск завершился аварийно: падение нативного кода,
  сигнал 6 (SIGABRT…)» и строки logcat упавшего процесса (`DiagLog.logCrashDetails`); последняя строка
  перед падением туннеля — «tun2socks: запуск → …».

## Уроки (что нашёл стенд и чего он не нашёл)

- 0.8.5: поток DNS переполнял пул ByeDPI → `-c 4096`, UDP-тайм-аут hev 20 с (поток DNS в `test-tun.sh`).
- 0.8.6: IPv6 в VPN без IPv6 у оператора — сайты с AAAA не открывались (стенд с `routes 1`).
- 0.8.7–0.8.8: соцсети и Telegram — модель ТСПУ по журналу, запасной путь через Psiphon, QUIC к Meta
  отбрасывается (`--udp-drop`).
- 0.8.9: «медленно» = обход вообще не подключался (UDP-DNS к 1.1.1.1 закрыт) → запасные DNS; задержка
  0,2 с на каждое соединение — hev слал приветствие SOCKS с `MSG_MORE` (найдено разбивкой «DNS/TCP/TLS/
  первый байт» и `strace -tt` на hev) → `oda-hev.h`; без задержки поток DNS снова переполнял пул →
  ByeDPI закрывает DNS-ассоциацию через 2 с после ответов (сразу — нельзя: A и AAAA с одного сокета,
  поймал только CI с IPv6 → проверка `dnspair`).
- 0.8.10: вылет из-за флагов сборки (см. выше) — стенд не видит, ловит CI-проверка APK и журнал.
- 0.11.2: «мусор» в соединении — tun2socks слал мелкие записи с алгоритмом Нейгла: при нескольких записях
  подряд (HTTP/2, TLS) каждая ждала подтверждения предыдущей, ByeDPI/Psiphon подтверждают через ~40 мс →
  +40 мс на ответ. Найдено новым замером `smallwrites` (3 × 100 байт и ответ, сервер «чата» на порту 8080
  в `lab.py`): 44 мс → 6,5 мс после `TCP_NODELAY` в `oda-hev.h` (через `setsockopt(IPV6_V6ONLY)` из
  `hev_socks5_socket`; `netinet/tcp.h` туда подключать нельзя — `TCP_MSS` спорит с lwIP). Заодно модель
  «Psiphon» стенда получила `TCP_NODELAY` (как настоящий на Go): её +40 мс к первому байту были ошибкой
  стенда. Модель ТСПУ не учитывает фейки с малым TTL (иначе исход «fake ttl 5» зависел от гонки, CI мигал).
- Отладка: мини-стенд в scratchpad (netns + srv + hev + ByeDPI без перебора) и `strace -f -tt` на hev
  быстрее полного прогона, когда ищешь, где теряется время.

## Особенности окружения

- **Нет IPv6 в ядре** (облачные контейнеры): hev всегда открывает сокеты AF_INET6, поэтому стенд сам
  собирает `scripts/tunlab/v4shim.c` (LD_PRELOAD, AF_INET6 → AF_INET) и убирает `ipv6:` из конфига hev.
  На раннере CI IPv6 есть: там ByeDPI пишет адреса как `::ffff:a.b.c.d`, а curl шлёт A и AAAA — как на Android.
- **Права**: программы стенда работают от uid 2000/2001, а домашняя папка раннера CI им закрыта —
  всё, что они читают и пишут, лежит в `$TMP` (`lab.py`, `tspu.py`, классы, `$TMP/out` для перебора).
- **Раннер CI отличается от контейнера** (учтено, но при правках стенда помнить): sysctl в новых netns
  наследуются от системы — `rp_filter` выключается во всех netns, `forwarding` ставится на каждом
  интерфейсе модели (без `tspu.py` «оператор» пакеты не пересылает); ядро отдаёт пакеты в TUN
  с недосчитанной контрольной суммой (offload veth) — `tspu.py` пересчитывает суммы TCP/UDP.
  Если через модель не идут пакеты, стенд сразу печатает правила, маршруты, sysctl и счётчики.
- **Процессы**: в фоне запускается подоболочка функции (NS/APP/TUNNEL), программа — её потомок;
  останавливать — `stop_pids` (гасит потомков), иначе порты останутся занятыми. `pkill -f` с шаблоном,
  который есть в собственной командной строке, убьёт и саму оболочку — гасить по PID.
- Если прогон прерван и netns остались: `sudo python3 scripts/tunlab/lab.py down`.

## Эмуляторы: полная проверка приложения (job «ui»)

Настоящий APK в эмуляторе Android на раннере GitHub (KVM) проходит экраны как человек; каждый экран —
скриншот и проверки по дереву элементов (uiautomator). Сценарий — `scripts/ui-test.py`:
1. **Ключ**: экран ключа без ключа; ключ вводится строчными без дефисов — форматируется на лету;
   «Активировать» → главная.
2. **Главная**: тексты не налезают друг на друга (`overlaps()`), видны строки способа и приложений, кнопка,
   статус, карточки, навигация; полоса «Ключ: осталось 5 минут» — по-русски при английском Android.
3. **Способ**: Psiphon → лист закрылся сам, способ сменился, нижние карточки на месте; обратно «Авто»;
   лист приложений.
4. **Меню ☰**: информация о ключе (ключ и «Продлить в Telegram»), как купить, инструкция, вопросы,
   конфиденциальность, о приложении; **вкладки** История и Настройки (с прокруткой).
5. **Подключение**: кнопка → «ОК» в системном окне VPN → «Подключено» (до 90 с) → тест скорости → смена
   способа при подключении; история.
6. **Конец срока ключа** (300 с + минута): при открытой главной ODA сама показывает «Тариф закончился»,
   `tun0` нет (VPN отключён).
7. **Падения**: буфер `logcat -b crash` — только процессы ODA (пакет `com.example.vpnapp`, в том числе
   `libpsiphon.so` из APK); при падении — полный отчёт и tombstone (`adb root`).
Итог — «UI: OK» или «UI: ОШИБКА — …» (job красный).

### Как запустить
1. **Тестовый ключ на 5 минут** в боевой базе бота (токены — у владельца, в репозиторий не писать):
   ```bash
   cd bot/worker && KEY=$(python3 -c "import secrets;A='ACDEFGHJKMNPQRTUVWXYZ234679';print('ODA-'+'-'.join(''.join(secrets.choice(A) for _ in range(4)) for _ in range(3)))") && \
   CLOUDFLARE_ACCOUNT_ID=3cc3b8392c90e87c7bc726e6b2c5fb9b CLOUDFLARE_API_TOKEN=<у владельца> npx --no-install wrangler d1 execute DB --remote \
     --command "INSERT INTO keys(key,tg_id,tariff,days,seconds,devices_max,created_at,created_by) VALUES('$KEY',0,'custom',1,300,2,unixepoch(),6866284629)" && echo $KEY
   ```
   `devices_max` — не меньше числа эмуляторов (каждый — своё устройство); срок идёт с первой активации.
   Один ключ — на один прогон (после него он истёк).
2. Запушить ветку, запустить workflow «Build APK» вручную с ключом: `mcp__github__actions_run_trigger`
   (`run_workflow`, `workflow_id: build.yml`, `ref: <ветка>`, `inputs: {"test_key": "<ключ>"}`). Если
   входной параметр только что добавлен, запуск до пуша падает («Unexpected inputs»).
3. Job «build» собирает телефонный APK (только ARM, артефакт `vpn-app-debug`) и **APK для эмулятора**
   (`ODA_ABIS=x86_64` для скриптов сборки Snowflake/Psiphon/ByeDPI, `./gradlew assembleDebug -PodaEmulator`,
   проверка, что в нём все `lib/x86_64/*.so` и нет ARM; артефакт `vpn-app-emulator`). Job «ui» — матрица
   API 35 и 36 (google_apis x86_64, `pixel_8`, `reactivecircus/android-emulator-runner@v2`), параллельно.
   Весь прогон ~25–30 минут: не опрашивать в цикле — `send_later` на 30 минут и ответить владельцу.

### Как читать результат
- Журнал job: `mcp__github__get_job_logs` (без `return_content`) → `logs_url` → `curl -sSL -o job.txt "<url>"`
  (ссылка живёт ~10 минут). Скриншоты в журнале — строки `@@SHOT <имя> <base64 JPEG>` (большие), поэтому:
  `grep -v "@@SHOT" job.txt | sed 's/^[0-9TZ:.-]* //' | grep -E "✓|✗|^[0-9]\)|экран|UI:|подключение в"`.
  Строка «экран NN-имя: …» — тексты на экране (видно, что именно показано, без картинки).
- Падение: текст между `---- logcat -b crash ----` и `---- конец отчёта ----` (процесс, сигнал, бэктрейс).
- Картинки: `mcp__github__actions_list` (`list_workflow_run_artifacts`) → `ui-shots-android-<API>` →
  `mcp__github__actions_get` (`download_workflow_run_artifact`) → `curl` zip в scratchpad → лист из 10
  уменьшенных PNG (PIL, 270×600 на кадр) → посмотреть через Read. Смотреть глазами: обрезанные тексты,
  наложения, лишние окна, повторы, старые тексты.

### Уроки (27.10.2026, 0.12.0–0.12.3)
- **Только ARM-APK на эмуляторе x86_64 падает в Go** (`libpsiphon.so` — SIGSEGV, `libgojni.so` из IPtProxy —
  SIGILL через tgkill, процесс `ndk_translation_program_runner…`): трансляция ARM→x86. На телефонах её нет.
  Отсюда отдельный APK x86_64 для эмулятора; после него VPN подключился на Android 14, 15 и 16.
  Не делать вывод «приложение падает» по ARM-коду на x86-эмуляторе.
- **Системные окна эмулятора** («Pixel Launcher isn't responding» при загрузке, запрос плитки в шторку)
  закрывают ODA — все шаги промахиваются. `ui-test.py` ждёт `sys.boot_completed`, разблокирует экран
  и закрывает такие окна в каждом `wait()` (`SYSTEM_DIALOGS`). Новое системное окно — добавить туда.
- **Падает служебный UiAutomation** самого теста («Bad file descriptor») — в буфере crash, но это не ODA;
  считаются только строки с пакетом ODA.
- Найденные ошибки приложения: «осталось 5 минуты» на английском Android (plurals берутся по языку
  системы → `Ui.plural` по-русски); выбор способа терялся без «Сохранить» (теперь применяется сразу);
  окно «добавить плитку» само после первого подключения (убрано); срок ключа вышел при открытой главной —
  «Ошибка подключения» и старая полоса до перезапуска (главная проверяет ключ раз в минуту, `keyTick`);
  на «Тариф закончился» красная строка повторяла заголовок.
- Скриншот сразу после открытия листа ловит анимацию — пауза 1,5 с перед `shot()`.
- Проверки по `resource-id` (`rid=…` — id из layout) надёжнее, чем по тексту; тексты — для того,
  что видит человек (склонения, повторы).

### Расширение проверки
- Новый экран или кнопка — шаг в `main()` `ui-test.py`: `tap(rid=…)`/`tap(text=…)`, `wait(…)`, `shot("имя")`,
  `ok(условие, "что проверено")`; наложения — `overlaps()`.
- Другой Android или телефон — значения в `matrix.api` и `profile` в job «ui» (каждый эмулятор — ещё одно
  устройство ключа: поднять `devices_max`).
- Эмулятор не ловит: настоящий ТСПУ и сеть оператора (это стенд и журнал телефона), особенности ARM-сборки
  (их ловят проверки APK в job «build»), оболочки производителей (MIUI и т. п.) — журнал с телефона.

## Расширение стенда сети

- Новый сайт «интернета»: имя и IPv4 в `SITES` в `lab.py` (сертификат, DNS и UDP-эхо подхватят сами).
- Новое поведение ТСПУ: профиль или параметр в `tspu.py`; проверка — в `apps_check`/секциях
  `test-tun.sh` через `check <0|1> "текст"`; контроль, который должен падать на старом коде, — как «!».
- Новый замер: функция в `test-tun.sh` (как `speed_run`) с `curl -w` по этапам и сравнением с прямым
  соединением (`APP curl --resolve …` — мимо VPN).
- После изменений: `bash scripts/test-bypass.sh` и этот стенд; после изменений интерфейса — ещё прогон
  эмуляторов (раздел выше); README («Сборка», «Этапы», «Опыт») и этот скилл держать в актуальном состоянии.

### Такая же имитация для другого приложения

1. **Телефон** — netns с TUN-интерфейсом, который поднимает настоящий нативный код приложения (или его
   сборка для Linux), и маршрутом по умолчанию в TUN; то, что Android исключает из VPN, — от отдельного
   uid с `ip rule uidrange` в свою таблицу.
2. **Оператор** — netns-маршрутизатор; поведение блокировок — программа на TUN (как `tspu.py`) с профилями
   по журналам пользователя; суммы TCP/UDP пересчитывать, `forwarding`/`rp_filter` задавать явно.
3. **Интернет** — netns с адресами из журналов на `lo`, DNS-сервер с этими адресами, HTTPS с CA стенда
   (SAN на все имена), эхо-серверы для протоколов без TLS и UDP.
4. **Код приложения** — тот же, что в APK: Java-логика без Android — через заглушки (`DiagLog`,
   `androidx.annotation`) и помощник вроде `TunLab`; нативное — из тех же исходников и с теми же флагами.
5. **Проверки** — измеримые («200 за < 3 с», «первый байт < 0,1 с», «pool is full: 0»), каждая —
   строкой ✓/✗; контроль со старым кодом, который должен падать; итог одной строкой для CI.
6. **CI** — тот же скрипт шагом workflow до сборки APK, плюс проверки самого APK (что не видно на стенде).
