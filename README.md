# ODA

Android-приложение: нажимаете кнопку → весь трафик телефона идёт в обход блокировок.
Три способа без своих серверов и без ключей: **обход DPI** (прямое соединение), **Psiphon**
и **Tor**. В режиме «Авто» они запускаются одновременно, работает тот, кто подключится первым.

Статус: **этапы 2–8**: Tor внутри приложения, VPN для всего телефона, мосты, журнал,
Tor без перезапусков, свой Snowflake с маскировкой DTLS, Psiphon, обход DPI (версия 0.8),
приложения соцсетей и Telegram при обходе DPI (0.8.7–0.8.8), скорость: обход DPI вместо Psiphon (0.8.9),
без вылетов (0.8.10). **0.8.10 на телефоне (27.10.2026, Redmi Note 8, мобильная сеть РФ): сайты, соцсети
и Telegram открываются, YouTube быстрый, вылетов нет** — подробности в «Опыт 0.8.6–0.8.10».

## Как это работает
- Кнопка → системный запрос «Разрешить VPN» → в режиме «Авто» **одновременно** запускаются
  обход DPI, Psiphon и Tor. Работает тот, кто подключится первым, остальные останавливаются.
  Исключение (с 0.8.9): если первым успел Psiphon, обход DPI продолжает перебор, и когда найдёт
  стратегию, открывающую соцсети, подключение переходит на него — он быстрее (журнал:
  «Переключаюсь с Psiphon на обход DPI»); Psiphon остаётся запасным путём.
- Обход DPI (см. ниже) — самый быстрый: прямое соединение без заграничного сервера.
- Psiphon обычно подключается за секунды и проходит там, где Tor заблокирован.
- Tor (`info.guardianproject:tor-android`) запускается с `ExitNodes {страна}` и `StrictNodes 1`.
- Tor запускается **один раз** за время жизни приложения. Мосты и страна для каждой попытки
  меняются командами через порт управления (как в Orbot), при отключении у Tor выключается
  сеть (`DisableNetwork 1`). Скачанная карта сети не теряется между попытками.
- Пока туннель не готов, VPN уже поднят и **блокирует** трафик, чтобы ничего не ушло мимо.
- Весь TCP-трафик телефона: VPN-интерфейс → tun2socks
  ([hev-socks5-tunnel](https://github.com/heiher/hev-socks5-tunnel), собирается
  через NDK) → локальный SOCKS5 Psiphon или Tor.
- DNS: фиктивный DNS (mapdns) внутри tun2socks; имена сайтов резолвит сервер Psiphon
  или выходной узел Tor, DNS-запросы провайдеру не уходят.
- IPv6 тоже заворачивается в туннель (не утекает мимо).
- UDP через туннель не идёт: такие пакеты отбрасываются (звонки в мессенджерах,
  QUIC, игры работать не будут; браузеры сами переходят на TCP).
- Kill switch: кнопка «KILL SWITCH» открывает системные настройки VPN — включите
  для ODA «Постоянная VPN» и «Блокировать соединения без VPN».
- «Проверить в браузере» — встроенный WebView через туннель
  (check.torproject.org для Tor, ipleak.net для Psiphon).

## Обход DPI (ByeDPI) — без сервера и без ключей
Главный способ для раздачи: подключаться могут все, никому не нужны серверы, ключи или подписки.
[ByeDPI](https://github.com/hufrea/byedpi) (MIT) не строит туннель за границу — он поднимает
локальный SOCKS-прокси на самом телефоне и меняет форму первых пакетов TCP (режет TLS
ClientHello и т.п.), чтобы ТСПУ не узнал протокол и не оборвал рукопожатие. Вы соединяетесь
с сайтом **напрямую**, блокировать по адресу нечего.
- Ядро `libbyedpi.so` (git-подмодуль `app/src/main/jni/byedpi`, собирается `scripts/build-byedpi.sh`
  через NDK) приложение запускает отдельным процессом; tun2socks заворачивает трафик в его SOCKS.
- DNS при обходе DPI: реальный резолвер, запросы идут через SOCKS (UDP) напрямую, как в ByeDPIAndroid.
  С 0.8.9 резолвер выбирается: 1.1.1.1, 8.8.8.8, 9.9.9.9, 77.88.8.8 (`NetProbe.DNS_SERVERS`) —
  первый, кто ответил через выбранную стратегию (в журнале «DNS телефона: 9.9.9.9 …», если не 1.1.1.1).
  В журнале 0.8.8 оператор не пропускал UDP-DNS к 1.1.1.1: все стратегии отвергались («DNS через
  обход не отвечает»), хотя соцсети через них открывались, — и всё шло через медленный Psiphon. mapdns (для Tor/Psiphon) здесь не используется: при прямом соединении
  имена должны резолвиться по-настоящему, а не в «фейковые» адреса.
  Каждый DNS-запрос телефона — отдельная SOCKS-UDP-ассоциация в ByeDPI, поэтому ByeDPI
  запускается с запасом соединений (`-c 4096`), а tun2socks закрывает UDP-сессию после 20 с
  без данных (`udp-read-write-timeout`), а не через 60 с (см. «Ошибка 0.8.5»).
- Цель — открыть заблокированные сайты (соцсети) и **не сломать обычный интернет**: через обход DPI
  идёт весь трафик телефона, включая российские сайты. Выбор стратегии (`BypassSearch`):
  - **Проверка как у браузера** (`NetProbe.bypassQuality`): DNS напрямую (все серверы
    `DNS_SERVERS` сразу; строка «DNS напрямую: 1.1.1.1 −, 8.8.8.8 +, …»), соединение по IP через SOCKS (как tun2socks), TLS с SNI и проверкой
    сертификата, запрос и чтение ответа — нужно получить 20 КБ или весь ответ, иначе
    «замороженное» соединение сошло бы за рабочее. Проверяются сразу:
    заблокированные (instagram, facebook, x, rutracker), обычные зарубежные (google, cloudflare,
    wikipedia) и российские (ya, vk, gosuslugi). Одновременно — **DNS как у телефона**: запрос
    ко всем серверам `DNS_SERVERS` через SOCKS5 UDP ASSOCIATE того же ByeDPI; берётся первый по порядку
    из ответивших (в строке проверки «· DNS 9.9.9.9», если не 1.1.1.1), он и станет DNS телефона.
    Не ответил ни один — стратегия не годится («DNS через обход (UDP …) не отвечает»): без DNS
    у телефона нет интернета, даже если сайты по IP открываются.
  - **Эталон** — те же сайты напрямую, без VPN (строка «Сеть напрямую» в журнале).
  - Стратегия **«полная»**, только если открыла заблокированный сайт И обычные сайты через неё
    работают не хуже эталона и лучшей из проверенных (допуск — один сайт). Пробивает, но ломает
    обычные — **не берётся никогда** (в журнале «ЛОМАЕТ обычные сайты — не беру»).
  - **Мягкие** стратегии (`-s 1+s` split SNI, `-d 1+s` disorder SNI) только режут ClientHello
    на TCP-части и запускаются сами по себе.
  - **Сильные** (OOB, disoob, fake с TTL 3/5/8, multidisorder, tlsrec) — только в **безопасной
    цепочке** ByeDPI: `-T 4:0:0:1 <мягкая> -A t,r,s <сильная>`. Все сайты идут через мягкую;
    если соединение с ней не прошло (таймаут 4 с, сброс, вместо ServerHello пришло другое),
    ByeDPI сам переподключается через сильную, повторяет запрос и запоминает IP сайта.
    Обычные сайты сильная стратегия не трогает. Так советует README ByeDPI: OOB и tlsrec путают
    мидлбоксы. `:0:0:1` после первых байт от сервера выключает таймаут, чтобы долгие соединения
    не рвались при коротких провалах мобильной сети.
  - Проверяется **по 3 стратегии одновременно** (у каждой свой процесс ByeDPI и порт 10809–10811).
    Пачки: запомненная для этой сети + мягкие; затем цепочки по три. Полная стратегия, пробившая
    3 из 4 заблокированных, берётся сразу; иначе перебор до конца и берётся лучшая (её процесс
    перезапускается и проверяется ещё раз).
  - **Нет полной — честно «только обычные сайты»**: берётся лучшая по обычным сайтам, под кнопкой
    пометка, что соцсети в этой сети обход DPI не открывает (похоже, блокировка по IP).
  - Выбор запоминается **для каждой сети** (Wi-Fi, мобильный оператор): в следующий раз
    запомненная проверяется первой. Если полный перебор не нашёл стратегию для соцсетей,
    в режиме «Обход DPI» 12 часов сразу включается запомненная для обычного интернета,
    без нового перебора (в «Авто» — нет: там соцсети могут открыть Psiphon и Tor).
  - Полный перебор (первое подключение в сети) — около минуты и ~3 МБ трафика; дальше — 10–20 секунд.
  - Если процесс ByeDPI завершился после подключения, это видно в журнале, и он перезапускается
    (до 3 раз).
- **Список заблокированных доменов** (`BypassProfile.BLOCKED_HOSTS`: Instagram и его CDN, Facebook/fbcdn,
  Messenger, Threads, WhatsApp, X, сайты Telegram, rutracker, LinkedIn, Discord, Signal, torproject; вместе
  с поддоменами). Для них в выбранной цепочке сильная стратегия идёт **сразу**, без попытки через мягкую
  (группа ByeDPI `-V 443 -H :<список> <сильная>`). Остальной трафик — как раньше: мягкая, при сбое сильная.
  Стратегия и проверка не меняются: перебор выбирает ту же цепочку, список — это то, как ByeDPI запускается
  с ней (`BypassProfile.route`; запомненные прошлыми версиями цепочки получают тот же маршрут).
- **QUIC к Meta отбрасывается** (с 0.8.8, в цепочке): приложения Instagram/Facebook/WhatsApp ходят
  в первую очередь по QUIC (UDP 443), а его ByeDPI не меняет — ТСПУ режет или «подвешивает». Группа
  `-K u -V 443 -j :<сети Meta> --udp-drop` отбрасывает такие датаграммы, и приложения уходят на TCP, где
  их открывает стратегия. QUIC к остальным (YouTube/Google и др.) идёт как раньше. `--udp-drop` — правка
  ODA к ByeDPI (ниже, «Сборка»).
- **Запасной путь (режимы «Авто» и «Обход DPI»):** если подключился обход DPI, Psiphon не останавливается
  (в «Обходе DPI» — запускается только для этого), а дальше подключается в фоне. Когда он готов, ByeDPI отправляет через него только то, что напрямую не открывается:
  - Telegram (сети Telegram, `BypassProfile.TELEGRAM_NETS`) — сразу; пока Psiphon не готов — напрямую;
  - соединение, которое не прошло ни через мягкую, ни через сильную стратегию (и сайты из списка, если
    сильная не прошла) — ByeDPI повторяет его через Psiphon и запоминает адрес: следующие соединения
    к нему сразу идут через Psiphon (так открываются адреса, закрытые по IP, например CDN картинок).
  Устроено так: у ByeDPI есть группы с `-C socks5://127.0.0.1:10808`, на этом порту — `HelperRelay`
  (в приложении), который принимает запрос SOCKS от ByeDPI и повторяет его в SOCKS Psiphon. Адрес IPv4,
  который ByeDPI с IPv6-сокетами (как на Android) передаёт в виде `::ffff:a.b.c.d`, он отдаёт обычным IPv4
  (так ByeDPI делает при IPv6-сокетах; как такой адрес примет сервер Psiphon — не проверено, поэтому
  переписывается). Пока идёт выбор стратегии или Psiphon
  не готов, путь закрыт (соединение сбрасывается, ByeDPI берёт следующую группу) — проверки стратегий
  он не искажает. Весь остальной трафик идёт напрямую, как раньше. Под кнопкой видно, готов ли запасной путь.
  В «Обходе DPI» Psiphon никогда не становится основным способом: только запасной путь (в 0.8.7 его
  там не было, и Telegram в этом режиме не мог открыться вовсе).
- **Своя строка ByeDPI** («СПОСОБ» → поле аргументов): тогда перебора нет, используется только она
  (как есть, даже если ломает обычные сайты — в журнале будет предупреждение). Пример цепочки:
  `-T 4:0:0:1 -s 1+s -A t,r,s -o 1+s`. Порт и адрес приложение задаёт само.
- **Сводка ByeDPI в журнале** (каждые 30 с, строка «ByeDPI за 30 с: …»): ByeDPI запускается с подробным
  выводом (`-x 1`), приложение разбирает его (`ByeDpiStats`) и пишет, сколько соединений прошло через
  какую группу («список → disoob SNI 12, split SNI 70, Psiphon после сбоя 3»), какие адреса понадобилось
  повторить другой группой («после сбоя: i.instagram.com 57.144.62.34 → disoob SNI после сбоя ×2») и какие
  не открылись ничем («не открылись ничем: scontent-…cdninstagram.com 157.240.x.x ×6, 149.154.167.51
  (Telegram) ×4») — с именем сайта из ClientHello или владельцем адреса (Telegram, Meta, Cloudflare, Google).
  Для новых таких адресов проверяется **почему** (`NetProbe.whyUnreachable`): напрямую TCP и TLS с другим,
  незаблокированным именем. Сервер отвечает на другое имя — режут по имени/виду трафика, стратегия
  не пробила; молчит или сбрасывает и с другим именем — блокировка по адресу, обход DPI её не берёт.
  Строка «Запасной путь (Psiphon): соединений N, к телефону M КБ» — сколько трафика ушло через Psiphon.
  «QUIC (UDP 443): Meta 12, Google 3» — сколько потоков QUIC и к кому (к Meta — отброшены).
  В 0.8.7 строки «почему» не появлялись (сводка стирала адреса раньше проверки) и в журнал попадали
  отладочные «send: pos=…» — исправлено, полноту фильтра проверяет `scripts/test-bypass.sh` по исходникам.
- **Где не прошёл заблокированный сайт** (с 0.8.8): в строках проверки у «−» причина — `instagram-(TLS)`
  (нет ответа на рукопожатие), `(сброс)`, `(TCP)`, `(16 КБ)` (данные пошли и «замёрзли»), `(серт.)`.
  После прямой проверки — строка «Заблокированные напрямую: instagram: …по адресу; facebook: …по имени…»:
  какие закрыты по IP (обход DPI их не откроет, нужен запасной путь), а какие — по имени (DPI).
- **Как читать журнал:** «Обход DPI (стратегия): итог; заблокированные N/4, обычные N/6
  (российские N) · instagram+ facebook- x- rutracker- | google+ … | ya+ …» — что открылось (+),
  что нет (−). Строка «Адреса заблокированных сайтов …» — какие IP им дал DNS (подменённый DNS тоже виден).
- **Если ни одна стратегия не пробивает соцсети** (в журнале «Скорее всего, соцсети здесь закрыты
  не по DPI, а по IP»): оператор режет их способом, который ByeDPI не берёт (например, по IP).
  Тогда остаются Psiphon/Tor («Авто») или свой сервер (VLESS/Reality через sing-box — отдельная
  крупная задача, нужен свой VPS).
- **Ошибка 0.8.4:** стратегия «oob SNI» (`-o 1+s`) прошла разовую проверку соцсети и была выбрана,
  после чего не открывался даже браузер. Проверка тогда не ждала обычные сайты и не проверяла
  российские вовсе, а OOB шёл на весь трафик. Вероятная причина поломки: OOB-байт часть серверов
  и «нормализаторов» TCP (межсетевые экраны, защита от DDoS) не вырезает, а вставляет в поток —
  ClientHello портится (на устройстве не подтверждено).
  С 0.8.5 OOB только в безопасной цепочке, а выбор требует, чтобы обычные сайты работали.
- **Ошибка 0.8.5:** обход DPI «подключился» (стратегия выбрана правильно, проверка IP прошла),
  но на телефоне не открывалось ничего. Причина найдена на стенде (`scripts/test-tun.sh`), а не
  в стратегии: цепочка `-T/-A` трафик через tun2socks не ломает. Каждый DNS-запрос телефона
  идёт с нового порта, и tun2socks открывает на него SOCKS-UDP-ассоциацию в ByeDPI и держит её
  60 с; ByeDPI тратит на неё 3 места пула (по умолчанию ~1000 мест, `-c 512`). Как только
  телефон начинает активно резолвить имена, пул переполняется (`add_event: pool is full`),
  и ByeDPI перестаёт принимать **любые** соединения — интернета нет, пока старые ассоциации
  не истекут. Проверки ODA шли один раз сразу после подключения, до наплыва запросов, и мимо VPN,
  поэтому ошибку не видели. С 0.8.6: `-c 4096`, UDP-сессии tun2socks — 20 с; DNS через
  SOCKS-UDP — в проверке стратегии; после подключения работает **сторож**.
- **IPv6 при обходе DPI** направляется в VPN, только если он есть у сети оператора (в журнале
  «IPv6 есть/нет» в строке подключения). Иначе приложения пробовали сайты с AAAA-записями
  (Google, YouTube, Instagram, Яндекс) по IPv6: tun2socks принимает соединение раньше, чем ByeDPI
  узнаёт, что IPv6 нет, и приложение получало сброс «установленного» соединения вместо отката
  на IPv4 (видно в имитации на раннере CI с IPv6). Для Tor/Psiphon IPv6 по-прежнему в туннеле.
- **Сторож после подключения** (каждые 30 с): DNS через SOCKS-UDP ByeDPI и сайт через него
  (`generate_204`, почти без трафика). Не прошло два раза подряд, а напрямую сайт открывается —
  ByeDPI перезапускается (до 3 раз). Если не открывается и напрямую — это пропала сеть, сторож ждёт.
  В журнал — счётчики tun2socks («Туннель: от телефона N пакетов…, к телефону M…»: если к телефону
  почти ничего не идёт, трафик стоит) и ошибки ядра ByeDPI («ByeDPI: … ×N»).
- **Приложения Instagram/Facebook/Telegram в 0.8.6** (браузер, поиск и YouTube работали, приложения
  соцсетей и Telegram бесконечно грузились; цепочка «split SNI → disoob SNI», проверка ODA открывала
  www.instagram.com и www.facebook.com). Что было видно в журнале и что изменено в 0.8.7:
  - «ByeDPI: recv: Connection timed out» 13–40 раз за 30 с всё время работы — соединения, у которых
    данные не подтверждаются 4 с (`-T 4`), то есть пакеты пропадают. Сайт, открытый сильной стратегией,
    ByeDPI запоминает по адресу, и ошибки для него прекращаются. Раз они не прекращались, приложения
    ходили на адреса, которые не открывала ни мягкая, ни сильная, а ByeDPI после такого сбоя забывает
    адрес и в следующий раз снова начинает с мягкой. Приложения ходят не на www, а на i.instagram.com,
    graph.facebook.com, CDN картинок (scontent-…cdninstagram.com, …fbcdn.net) и т.п.; часть CDN,
    по данным пользователей zapret, в РФ закрыта по IP. 0.8.7: сильная для этих доменов — сразу (имя
    сайта не уходит ТСПУ через мягкую, нет 4 с ожидания на каждый новый адрес), закрытое по IP —
    через запасной путь, а в журнале видно, какие именно имена и адреса не открываются и почему.
  - «split cancel: pos=0--1, n=256/186» — соединения без имени сайта в первом пакете (не TLS): так
    работает Telegram (MTProto) и чаты WhatsApp. Стратегии ByeDPI, которые режут имя сайта, их не меняют
    вовсе. С 2026 года ТСПУ замедляет и режет Telegram по адресам серверов и по виду трафика — это обход
    DPI не берёт. 0.8.7: в «Авто» Telegram идёт через Psiphon (запасной путь), остальное — напрямую.
  - QUIC (UDP 443) у приложений Meta и YouTube ByeDPI пропускает как есть; если ТСПУ его режет,
    приложения сами переходят на TCP (YouTube работал). Блокировать QUIC ByeDPI без правки ядра не умеет:
    фильтр портов `-V` в нём сравнивает порты в сетевом порядке байтов (работает только равенство).
  Без журнала с телефона не подтверждено, что именно закрыто по IP, — для этого и добавлены сводка и
  проверка «почему»; если по журналу 0.8.7 окажется, что соцсети режутся по IP целиком, обход DPI их
  не откроет — останется запасной путь Psiphon («Авто») или свой сервер (VLESS/Reality, нужен VPS).
- **Журнал 0.8.7** (режим «Обход DPI», YouTube работал, Telegram, Facebook и Instagram — нет) и 0.8.8:
  - ТСПУ изменился: OOB и disoob больше не пробивают, а `tlsrec+oob` и `tlsrec+disorder` — да
    (facebook, x, rutracker); instagram (31.13.72.174) не открыла ни одна стратегия. Перебор выбрал
    «split SNI → tlsrec+oob». Добавлены ещё две tlsrec-стратегии про запас.
  - Telegram (149.154.167.x) — «не открылись ничем» всё время: в режиме «Обход DPI» запасного пути не было.
    0.8.8: запасной путь работает и в этом режиме.
  - За 4 минуты приложения Meta открыли всего 6 TCP-соединений (все прошли через список доменов
    без сбоев), а сами висели — похоже, они сидели на QUIC. 0.8.8: QUIC к Meta отбрасывается.
  - Строки «почему» не появились из-за ошибки (исправлено); у YouTube мягкая стратегия срывалась,
    и его открывала сильная после сбоя (в журнале «после сбоя: redirector.googlevideo.com → …»).
  - Всё это воспроизводит модель ТСПУ на стенде (профиль `oct2026`, ниже): тот же выбор стратегии,
    те же «+» и «−»; с 0.8.8 на стенде открываются Facebook (сильной сразу), Instagram и CDN картинок
    (сильная не прошла → Psiphon, второй раз — сразу), Telegram (Psiphon), YouTube; QUIC к Meta отброшен.
- **Журнал 0.8.8** («Авто», Psiphon работает, соцсети открываются, но медленно): у всех стратегий
  «DNS через обход (UDP 1.1.1.1) не отвечает», хотя `tlsrec+oob` открывала instagram, facebook, x,
  rutracker. Обход DPI не подключился, и весь трафик шёл через Psiphon (сервер в США/Германии).
  0.8.9: запасные DNS-серверы (выше) и переход с Psiphon на обход DPI. На стенде — профиль `nov2026`
  (UDP-DNS к 1.1.1.1 и 8.8.8.8 режется) и замер скорости: обход против «Psiphon» (ниже, «Сборка»).
  **Задержка 0,2 с на каждое соединение** (найдена замером на стенде): tun2socks (hev-socks5-tunnel)
  отправлял приветствие SOCKS5 с флагом `MSG_MORE` и ждал ответа — ядро придерживало эти 3 байта до
  таймера, 200 мс. Каждый DNS-запрос телефона и каждое новое соединение ждали лишние 0,2 с (через обход
  DPI — DNS 0,2 с + соединение 0,2 с; через Psiphon и Tor — 0,2 с на соединение). С 0.8.9 hev собирается
  с `app/src/main/jni/oda-hev.h` (`-include`: `MSG_MORE` = 0 в файлах hev, подмодуль не меняется);
  на стенде первый байт через обход — ~0,01 с вместо 0,42 с. Режим `pipeline` hev не подходит: ByeDPI
  принимает приветствие SOCKS только отдельным пакетом.
  Без этой задержки DNS-ассоциации создаются быстрее, и пул ByeDPI переполнялся бы раньше (каждый
  запрос — своя SOCKS-UDP-ассоциация, 3 места пула, до тайм-аута tun2socks 20 с). Поэтому в правке ByeDPI
  (`scripts/byedpi.patch`) ассоциация к порту 53 закрывается целиком через 2 с после ответа на все её
  DNS-запросы (резолвер телефона на каждый запрос открывает новый сокет); tun2socks видит закрытие
  и тоже освобождает сессию. Сразу закрывать нельзя: A и AAAA идут с одного сокета, и второй запрос
  терялся (резолвер ждал повтора 5 с) — так было в первом прогоне CI с IPv6.
  Psiphon в журнале ещё писал «SOCKS … command was 0x03» — это tun2socks просит у него UDP (QUIC),
  а Psiphon UDP не передаёт; приложения после этого уходят на TCP, на скорость почти не влияет.
- **Ограничения:** обход DPI соединяет напрямую, поэтому нет выбора страны, нет анонимности, и сайт
  видит ваш настоящий IP. Помогает только против блокировки по DPI/имени сайта; против блокировки
  по IP и «белых списков» не поможет — там работает туннель (Psiphon/Tor). Поэтому в «Авто» обход DPI
  идёт первым, а Psiphon и Tor — как запас.

## Psiphon
[Psiphon](https://github.com/Psiphon-Labs/psiphon-tunnel-core) — открытая сеть обхода блокировок
(тысячи серверов). Он сам перебирает около десятка способов маскировки: OSSH, TLS, meek через CDN,
QUIC, in-proxy (через домашние IP добровольцев приложения Conduit). Адреса дата-центров ТСПУ режет
и замедляет, а домашние IP — гораздо реже.
- В APK лежит программа Psiphon (`libpsiphon.so`, ConsoleClient из psiphon-tunnel-core, собирается
  в CI скриптом `scripts/build-psiphon.sh`). Приложение запускает её отдельным процессом
  и заворачивает трафик в её локальный SOCKS-прокси.
- Список серверов (`assets/psiphon/server_list.txt`, около 430 серверов) скачивается при сборке,
  подпись проверяется ключом Psiphon. Первое подключение не ждёт загрузки списка.
  Дальше Psiphon сам обновляет список, данные лежат в `files/psiphon/data`.
- Страна выхода — параметр `EgressRegion` (страна сервера Psiphon). Если выбранной страны нет
  среди серверов Psiphon, выход будет в любой стране, под кнопкой это написано.
- Используется публичная конфигурация Psiphon: идентификаторы `FFFFFFFFFFFFFFFF` и публичный
  список серверов. Те же значения использует открытый клиент
  [warp-plus](https://github.com/bepass-org/warp-plus). Psiphon может в любой момент
  ограничить такие подключения, тогда останется Tor.
- **Psiphon не анонимен, как Tor:** сервер Psiphon видит, к каким сайтам вы обращаетесь
  (содержимое HTTPS он не видит). Нужна анонимность — выберите способ через Tor.
- Psiphon распространяется по лицензии GPLv3; исходники — по ссылке выше, коммит указан
  в `scripts/build-psiphon.sh`.

## Проверка сети и «белые списки»
При подключении приложение напрямую, мимо VPN, проверяет зарубежные сайты (google.com,
cloudflare.com, wikipedia.org), российские (ya.ru, vk.com, gosuslugi.ru) и заблокированные
(instagram, facebook, x, rutracker) — тем же способом, что и стратегии обхода DPI (это их эталон). Если российские
открываются, а зарубежные нет, у оператора, скорее всего, включены «белые списки». Их не обходит
ни Psiphon, ни Tor: под кнопкой появится подсказка подключиться к Wi-Fi. Результат проверки —
в журнале, строка «Сеть напрямую: …».

## Способы подключения
Кнопка «СПОСОБ» внизу экрана:

| Режим | Что делает |
|---|---|
| **Авто** (по умолчанию) | **Обход DPI, Psiphon и Tor одновременно**, работает тот, кто подключится первым. Обход DPI обычно быстрее всех; тогда Psiphon остаётся запасным путём для Telegram и адресов, закрытых по IP. Tor при этом пробует: 1) последний сработавший мост; 2) **Snowflake** (Google AMP, затем CDN77); 3) **другие мосты сразу**: Moat, свои, meek; 4) встроенные obfs4; 5) DNSTT; 6) без мостов |
| Обход DPI | Обход DPI (прямое соединение, без сервера); Psiphon — только запасной путь для Telegram и того, что закрыто по IP |
| Psiphon | Только Psiphon |
| Snowflake | snowflake через CDN77 и через Google AMP, с маскировкой DTLS (см. ниже) |
| obfs4 | Встроенные obfs4 (часто заблокированы) |
| meek | Маскировка под CDN, медленно |
| DNSTT | Туннель через DNS Google, очень медленно |
| Свои мосты | Строки из Telegram-бота **@GetBridgesBot** (`/webtunnel` — лучше всего, или `/obfs4`) |
| Без мостов | Прямое подключение |

Moat — служба Tor Project, которая выдаёт мосты под вашу сеть. Запрашивается двумя
путями параллельно: через meek (CDN77) и через DNSTT (Guardian Project). Подключение ждёт
Moat только при самом первом запуске в сети без блокировок; в остальных случаях Moat
спрашивается в фоне, и свежие мосты добавляются в план после текущей попытки.
В России, Беларуси, Китае, Иране, Туркменистане и Мьянме прямое подключение всегда последнее.

### Snowflake с маскировкой DTLS
С весны 2026 ТСПУ в России узнаёт Snowflake по первому пакету DTLS-рукопожатия (отпечаток JA3/JA4).
Клиент Snowflake умеет маскировать это рукопожатие под Chrome/Firefox (covert-dtls,
`covertdtls-config`), но Snowflake внутри IPtProxy этот параметр не читает. Поэтому с версии 0.6
в APK лежит свой клиент Snowflake Tor Project (`libsnowflake.so`, собирается в CI скриптом
`scripts/build-snowflake.sh`). Tor запускает его сам (`ClientTransportPlugin snowflake exec …`)
с `-covertdtls-config randomizemimic` и `-max 3`. Если в строке моста есть свой
`covertdtls-config=…`, он важнее. Если клиента в APK нет или он не запускается на телефоне,
берётся Snowflake из IPtProxy — в журнале это видно первой строкой «Snowflake: …».
Журнал клиента — в конце экрана «ЖУРНАЛ» (блок «Snowflake»); строки Tor вида
`Managed proxy "snowflake": broker failure …` значат, что не отвечает брокер (сигнальный сервер),
а не DTLS.

Важно при чтении журнала: с мостами (pluggable transport) Tor пишет 10% «Connected to a relay»,
как только подключился к **локальному** транспорту, ещё до связи с мостом. «Мост ответил» —
это строка `ORCONN … CONNECTED`.

Таймауты: пока ни один мост не ответил — 30–120 с (Snowflake 90 с, DNSTT 120 с без роста).
Как только с мостом прошло рукопожатие, канал считается рабочим, и попытка не обрывается
до 3 минут без роста (всего до 6 минут): Snowflake строит цепочку медленно.
Snowflake держит до 3 добровольцев одновременно, чтобы не рваться при отключении одного.

Под кнопкой видно, что пробуется и почему не идёт, по строке на способ:
«Psiphon: поиск сервера, попыток 40» и «2/4 Другие мосты · Tor 10% · нет ответа».
Ссылка **«ЖУРНАЛ»** под статусом показывает подробности (Psiphon, Tor, мосты);
кнопка «КОПИРОВАТЬ» копирует журнал, чтобы переслать разработчику.
Строки Psiphon в журнале: «попыток N (OSSH 12, TLS-OSSH 8, …)» — какими способами он пробует;
«сервер ответил (протокол, страна)»; «туннель через …» — чем подключился.

### Ограничения
- В странах с малым числом выходных узлов (JP, FI, CH) подключение медленнее.
- Многие сайты показывают капчу или блокируют Tor.
- Если оператор включил «белые списки» (мобильный интернет только к разрешённым
  сайтам), не поможет ни Psiphon, ни мосты: нужна другая сеть (Wi-Fi).

## Как получить APK на телефоне

APK собирает GitHub Actions после каждого push. Компьютер не нужен.

### 1. Дождаться сборки
1. Откройте репозиторий на github.com в браузере телефона
   (в приложении GitHub артефакты не скачиваются — нужен браузер).
2. Вкладка **Actions** (если её не видно — меню «⋯» или переключите сайт
   в режим «Версия для ПК»).
3. Сверху — последний запуск **Build APK**. Жёлтый кружок — идёт сборка
   (обычно 3–6 минут), зелёная галочка — готово, красный крестик — ошибка.
4. Запустить сборку вручную: Actions → **Build APK** → **Run workflow**.

### 2. Скачать
1. Нажмите на успешный запуск (зелёная галочка).
2. Пролистайте вниз до блока **Artifacts** и нажмите **vpn-app-debug**.
   Нужно быть залогиненным в GitHub.
3. Скачается архив `vpn-app-debug.zip`. Откройте его в приложении «Файлы»
   и извлеките `app-debug.apk`.

### 3. Установить
1. Нажмите на `app-debug.apk`.
2. Android попросит разрешить установку из неизвестных источников:
   **Настройки → Разрешить из этого источника** для приложения, через
   которое открыт файл («Файлы» или браузер). На старых версиях Android:
   Настройки → Безопасность → **Неизвестные источники**.
3. Вернитесь назад и нажмите **Установить**.
4. Google Play Защита может предупредить о незнакомом приложении —
   выберите «Всё равно установить» (APK подписан debug-ключом).

Новая версия ставится поверх старой. Если установка ругается на подпись,
удалите старую версию и поставьте заново (debug-ключ в облаке может меняться).

- Workflow: `.github/workflows/build.yml`.
- `scripts/test-bypass.sh` — проверка обхода DPI без Android SDK (нужны JDK и gcc, идёт и в CI):
  сценарии выбора стратегии и маршрута (`app/src/test/java/…/BypassSearchTest.java`), что каждую

  Профили ТСПУ подобраны по журналам телефона: `nov2026` (0.8.8: как `oct2026`, instagram по адресу не
  закрыт, UDP-DNS к 1.1.1.1 и 8.8.8.8 режется — DNS телефона должен стать 9.9.9.9), `oct2026` (0.8.7: OOB не пробивает, tlsrec — да; instagram,
  CDN и Telegram закрыты по адресу) и `jun2026` (0.8.6: OOB пробивает). Для каждого стенд запускает
  **настоящий перебор ODA** (`TunLab search`: прямая проверка, `BypassSearch` пачками по 3 процесса ByeDPI
  с маршрутом `BypassProfile.route`, `NetProbe`) и проверяет, что выбрана та же стратегия, что на телефоне,
  а затем «приложения» через VPN: обычные сайты, YouTube, Facebook и Instagram (как приложение),
  CDN картинок, Telegram, QUIC к Meta (отброшен) и к Google (идёт), NetProbe и сторож, сводку ByeDPI;
  для `nov2026` ещё — **скорость**: загрузка 32 МБ (cloudflare, facebook, i.instagram, googlevideo) через
  обход DPI и через «Psiphon» (как при подключении через Psiphon: hev с mapdns), обход должен быть
  минимум втрое быстрее и не медленнее 2 МБ/с, первый байт через обход — быстрее 0,1 с (ловит задержку
  hev 0,2 с), через «Psiphon» — не больше его задержки + 0,1 с; для сравнения — то же без VPN; для `oct2026` — поток DNS (100 запросов/с, без «pool is full»), закрытый запасной путь (всё прочее работает),
  «почему» (адрес или DPI) и контроль: запуск 0.8.6 — соцсети не открываются, поток DNS роняет интернет.
  Профили: `LAB_PROFILES="nov2026"`. Нужны gcc, make, patch, JDK, python3 + `pyroute2`, openssl, curl,
  procps. Без IPv6 в ядре hev работает через прослойку `scripts/tunlab/v4shim.c`. Модель — не настоящий
  ТСПУ: она проверяет устройство пути трафика и выбор стратегии на известном поведении; новое поведение
  ТСПУ видно только в журнале телефона.

База GeoIP (`app/src/main/assets/geoip`) — из Tor, данные IPFire Location
(CC BY-SA 4.0). Встроенные мосты (`assets/builtin-bridges.json`) — список Tor Project
(тот же, что в Tor Browser и Orbot).

## Опыт 0.8.6–0.8.10: от «не открывается» до «быстро»
Как приложение доводилось до рабочего состояния — чтобы следующие проблемы решать так же.

**Метод.** Пользователь присылает журнал («ЖУРНАЛ» → «КОПИРОВАТЬ»), стенд (`scripts/test-tun.sh`, скилл
`.claude/skills/phone-imitaion`) повторяет поведение оператора по этому журналу (профиль ТСПУ, адреса
сайтов), исправление делается в коде приложения и проверяется на стенде, затем в CI (там IPv6, как на
телефоне), затем новым журналом с телефона. Код на стенде настоящий (ByeDPI, tun2socks, перебор, проверки),
подделано только окружение — поэтому он находит ошибки самого приложения.

**Что было и что помогло:**
| Версия | Симптом на телефоне | Причина | Что сделано |
|---|---|---|---|
| 0.8.5 | «подключено», интернета нет | поток DNS переполнял пул ByeDPI | `-c 4096`, UDP-тайм-аут tun2socks 20 с |
| 0.8.6 | сайты с IPv6 не открывались | IPv6 в VPN без IPv6 у оператора | IPv6 в VPN только при IPv6 у оператора |
| 0.8.7 | Instagram, Facebook, Telegram висят | ТСПУ сменился (tlsrec вместо OOB), Telegram и CDN закрыты по адресу | список доменов сразу на сильную стратегию, запасной путь через Psiphon |
| 0.8.8 | приложения Meta висят | QUIC к Meta режется | QUIC к Meta отбрасывается (`--udp-drop`) — приложения уходят на TCP |
| 0.8.9 | работает, но медленно | UDP-DNS к 1.1.1.1 закрыт → все стратегии отвергались → всё через Psiphon; +0,2 с на каждое соединение в tun2socks (`MSG_MORE`) | запасные DNS, переход с Psiphon на обход, `oda-hev.h`, DNS-ассоциации ByeDPI закрываются через 2 с |
| 0.8.10 | вылет при подключении | флаги сборки tun2socks из Gradle затёрли `Application.mk` (JNI-класс) | флаги только в `Application.mk`, проверка APK в CI, подробности падений в журнале |

**Успешный журнал 0.8.10** (27.10.2026, «Обход DPI», мобильная сеть РФ), как выглядит рабочее состояние:
- «DNS напрямую: 1.1.1.1 −, 8.8.8.8 +, 9.9.9.9 +, 77.88.8.8 +» → «DNS телефона: 8.8.8.8 (1.1.1.1 через обход
  не отвечает)» — догадка 0.8.9 подтвердилась: UDP-DNS к 1.1.1.1 оператор не пропускает.
- Стратегия: «split SNI → disoob SNI» (заблокированные 3/4: facebook, x, rutracker; обычные 6/6). В 0.8.7
  пробивала только tlsrec, теперь disoob — ТСПУ меняется, поэтому перебор с запоминанием по сети важнее
  любой одной стратегии. При повторном подключении запомненная стратегия берётся сразу (~18 с до «Проверка IP»).
- instagram (157.240.205.174): «TCP напрямую не соединяется — похоже на блокировку по адресу» — его
  и `static.cdninstagram.com` несёт запасной путь («список → Psiphon»); Telegram — «Telegram → Psiphon».
- YouTube: мягкая стратегия на `i.ytimg.com`, `googlevideo`, `youtubei.googleapis.com` срывается, и их
  сразу открывает «disoob SNI после сбоя» — через Psiphon почти ничего не идёт, поэтому быстро.
- «tun2socks: запуск → SOCKS 127.0.0.1:10809, DNS 8.8.8.8 через SOCKS-UDP», «Проверка IP: … (RU)» —
  трафик идёт напрямую (свой IP), вылетов нет.
- Не мешает работе: «Psiphon ошибка: tunneled DSL fetch failed … missing public key» (у Psiphon нет ключа
  для подписи дополнительного списка серверов, основной список работает), «netlinkrib: permission denied» (Psiphon не видит маршруты IPv6
  на Android), «ByeDPI: recv: Connection timed out» и «split cancel: pos=0--1» (соединения без имени
  сайта — Telegram и т. п.).

**Уроки:**
- «Медленно» может значить «работает не тот способ»: сначала смотреть, через что подключено (`bypass`/`psiphon`)
  и почему отвергнут быстрый способ, а потом уже скорость.
- Замер задержки по этапам (DNS / TCP / TLS / первый байт) рядом с прямым соединением сразу показывает,
  где теряется время; `strace -tt` на tun2socks показал `MSG_MORE`.
- Убрав одно узкое место, проверять соседнее: без задержки tun2socks поток DNS снова переполнял пул ByeDPI.
- Проверять там, где есть IPv6 (CI): раннее закрытие DNS-ассоциации ломало только A + AAAA с одного сокета.
- Стенд не видит сборку под Android: флаги нативной сборки — только в `Application.mk`, а то, что видно
  лишь в APK (имя JNI-класса), проверяет CI. Журнал должен сам объяснять падения (сигнал, строки logcat
  упавшего процесса, последняя строка перед запуском туннеля).

### Вылет 0.8.9 и что изменено в 0.8.10
0.8.9 падал при подключении в любом режиме («Прошлый запуск завершился аварийно: причина 5, код 6» —
нативный SIGABRT), как только поднимался туннель. Причина — сборка tun2socks: флаг `-include oda-hev.h`
был задан в `app/build.gradle` (`cFlags`), а Gradle передаёт его ndk-build как `APP_CFLAGS+=…`
в командной строке make. Переменная из командной строки целиком заменяет `APP_CFLAGS` из `Application.mk`,
и пропали `-DPKGNAME=com/example/vpnapp -DCLSNAME=Tun2Socks`: `JNI_OnLoad` hev искал класс
`hev/htproxy/TProxyService`, и ART (CheckJNI в отладочной сборке) прерывал процесс при загрузке
библиотеки. Стенд и CI этого не видели: стенд собирает hev своим `make`, без JNI. В 0.8.10 все флаги —
в `Application.mk`, а CI проверяет в APK, что `libhev-socks5-tunnel.so` содержит имя класса
`com/example/vpnapp/Tun2Socks` и метку `oda-hev.h`. Чтобы следующую такую ошибку было видно сразу,
журнал после нативного падения или ANR добавляет строки logcat упавшего процесса («JNI DETECTED ERROR…»,
«Fatal signal 6 … (имя потока)»), а перед запуском tun2socks пишет строку «tun2socks: запуск …».

### Вылет версии 0.4 и что изменено в 0.5
В 0.4 приложение аварийно закрывалось («Прошлый запуск завершился аварийно: причина 5, код 6»,
нативный SIGABRT) при смене попытки: Tor останавливался и запускался заново в том же процессе.
`TorService` отпускает свою блокировку раньше, чем Tor реально завершился, и повторный запуск
в процессе ненадёжен (тикеты Tor #24581, #40989). В 0.5 Tor больше не перезапускается.

Важно для кода: процент bootstrap в Tor внутри процесса никогда не уменьшается, поэтому
после первой попытки готовность определяется по `status/circuit-established`
(сбрасывается при `DisableNetwork 1`), а «мост ответил» — по событию `ORCONN … CONNECTED`.

Следующий шаг, если вылеты останутся: вынести Tor и мосты в отдельный процесс (`:tor`, как в Orbot),
чтобы падение Tor не закрывало экран приложения.

## Как продолжить работу в новом чате Claude
1. Откройте новый чат Claude Code и подключите репозиторий **Wddis/Pol**.
2. Попросите прочитать этот README и код в рабочей ветке (последняя — та, где лежит самая
   новая версия из `app/build.gradle`; или `main`, если pull request уже влит).
3. Опишите задачу своими словами и приложите свежий журнал из приложения («ЖУРНАЛ» → «КОПИРОВАТЬ»).
   Для проверок без телефона — скилл `phone-imitaion` (`/phone-imitaion`): имитация телефона, оператора
   с моделью ТСПУ и интернета; порядок «журнал → профиль стенда → исправление → CI → журнал» — в разделе
   «Опыт 0.8.6–0.8.10».
4. Сборка: push в `main` и `claude/**` запускает GitHub Actions; для других веток —
   Actions → Build APK → Run workflow с выбором ветки. APK — в Artifacts как `vpn-app-debug`.
